Applications run on a Rust server with an embedded V8 runtime. The deployment workflow is straightforward: build your app, then start the server.

## Building for Production

Run `rari build` to create a production build:

```terminal
rari build
```

This cleans any previous `dist/` output, then runs three steps in sequence:

1. Type checks your project with `tsc`
2. Bundles your application with Vite
3. Pre-optimizes images referenced in your build

The output goes to `dist/`. This directory and your `node_modules` are everything the server needs to run your app.

## Starting the Server

Run `rari start` to launch the production server:

```terminal
rari start
```

The server binds to `127.0.0.1:3000` by default. On supported platforms (Railway, Render, Fly.io), it automatically binds to `0.0.0.0` so the host can route external traffic to your app.

## Environment Variables

| Variable    | Description                                                        | Default                                                     |
| ----------- | ------------------------------------------------------------------ | ----------------------------------------------------------- |
| `PORT`      | Server port                                                        | `3000`                                                      |
| `RSC_PORT`  | Alternative server port (fallback if `PORT` is not set)            | `3000`                                                      |
| `NODE_ENV`  | Environment mode                                                   | `production` for `rari start`, `development` for `rari dev` |
| `RUST_LOG`  | Rust runtime log level (`error`, `warn`, `info`, `debug`, `trace`) | `error`                                                     |
| `RARI_HOST` | Server bind address                                                | `127.0.0.1` (`0.0.0.0` on Railway, Render, and Fly.io)      |

`PORT` takes precedence over `RSC_PORT`. Most hosting platforms set `PORT` automatically.

## OpenTelemetry

rari can export traces, metrics, and logs from your server code to any [OpenTelemetry](https://opentelemetry.io) collector. It's off by default, and turns on when you set an OTLP endpoint:

```terminal
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 OTEL_SERVICE_NAME=my-app rari start
```

When it's on:

- Outgoing `fetch` calls, including cached ones, and `node:http` servers record spans. `fetch` adds a `traceparent` header so downstream services join the same trace. A cached response has the `rari.fetch.cached` attribute set to `true`.
- `console` output is also exported as log records.
- `@opentelemetry/api` reports to the same exporter, so you can add your own spans and metrics.

| Variable                      | Description                                                                                                                                | Default                |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------- |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Collector URL. Setting it turns export on.                                                                                                 | off                    |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf`, `http/json`, or `grpc`. `console` prints to stdout instead, for local debugging, and turns export on without an endpoint. | `http/protobuf`        |
| `OTEL_EXPORTER_OTLP_HEADERS`  | Headers sent to the collector, such as an API key (`key=value,key2=value2`)                                                                |                        |
| `OTEL_SERVICE_NAME`           | Service name attached to everything rari exports                                                                                           |                        |
| `OTEL_PROPAGATORS`            | Trace context formats `fetch` sends and reads (`tracecontext`, `baggage`, `none`)                                                          | `tracecontext,baggage` |
| `RARI_OTEL_CONSOLE`           | `capture` exports `console` output and also prints it, `replace` only exports it, `ignore` leaves it alone                                 | `capture`              |
| `OTEL_SDK_DISABLED`           | Set to `true` to turn export off even when an endpoint is set                                                                              |                        |

The other standard `OTEL_*` variables, such as `OTEL_RESOURCE_ATTRIBUTES` and `OTEL_TRACES_SAMPLER`, work too.

Spans from one request aren't yet grouped under a span for the request itself, so each outgoing call starts its own trace unless the code making it is already inside a span.

## Railway

rari has built-in support for [Railway](https://railway.app). Run the deploy command to generate the configuration:

```terminal
rari deploy railway
```

This creates a `.railway/railway.ts` file, Railway's [Infrastructure as Code](https://docs.railway.com/infrastructure-as-code) format, and updates your `package.json`:

```ts title=".railway/railway.ts"
import { defineRailway, github, project, service } from 'railway/iac'

export default defineRailway(() => {
  const app = service('my-app', {
    source: github('acme/my-app', { branch: 'main' }),
    start: 'npm start',
    healthcheck: '/_rari/health',
    healthcheckTimeout: 300,
    deploy: {
      restartPolicyType: 'ON_FAILURE',
      restartPolicyMaxRetries: 3,
    },
    env: {
      RAILPACK_DEPLOY_APT_PACKAGES: '... libfontconfig1',
    },
  })

  return project('my-app', { resources: [app] })
})
```

The service and project names come from the `name` in your `package.json`, without any npm scope. The `source` comes from your `origin` remote and current branch. If your project has no GitHub remote, `source` is left out and you connect the repository in the Railway dashboard instead.

Your `package.json` gets these changes:

- `scripts.start` is set to `rari start`
- `scripts.build` is set to `rari build` if not already present (Railway runs it during the build)
- `engines.node` is set to `>=24.21.0` if missing or lower (required by rari)
- `rari` is added to `dependencies` if not already present

If you have an existing `start` script, it's backed up to `start:original`. An existing `.railway/railway.ts` is backed up to `.railway/railway.ts.backup`.

### Deploying to Railway

The Railway CLI evaluates `.railway/railway.ts` with the `railway` package, so add it as a dev dependency:

```package-managers
pnpm: pnpm add -D railway
npm: npm install -D railway
yarn: yarn add -D railway
bun: bun add -d railway
```

Then:

1. Push your code to GitHub
2. Install the [Railway CLI](https://docs.railway.com/cli) and run `railway init --name my-app` to create a project and link it to your directory
3. Run `railway config plan` to preview the changes, then `railway config apply` to create the service and deploy it
4. Generate a domain under Settings → Networking

Railway needs access to your repository through its GitHub app. If `apply` can't find the repository, connect your GitHub account in the Railway dashboard first.

Railway doesn't read `.railway/railway.ts` during deploys. Run `railway config apply` again whenever you change it.

To manage an existing service instead, run `railway link` to link to its project, and change the name passed to `service()` to match the service in Railway.

Check the `railway config plan` output before applying. If the service name doesn't match, the plan creates a new service and deletes the existing one. Railway manages service variables from the file by default, so if your service has variables that aren't in `env`, the plan stops and asks you to declare them. Wrap any secret in `preserve()` (imported from `railway/iac`) to keep the value already set in Railway without committing it.

Railway is auto-detected via the `RAILWAY_ENVIRONMENT` environment variable, and the server binds to `0.0.0.0` with the platform-assigned `PORT`.

### System Dependencies

The Rust runtime requires `libfontconfig1` for image and font rendering. The generated `.railway/railway.ts` installs it in the deployed image through the `RAILPACK_DEPLOY_APT_PACKAGES` variable. The `...` entry keeps the packages Railpack would install anyway.

If your project already has a `railpack.json`, `rari deploy railway` adds `libfontconfig1` to its `deploy.aptPackages` instead, and leaves the variable out of `.railway/railway.ts`. A `deploy.aptPackages` list in `railpack.json` replaces the variable, so the package has to be in the file.

## Render

rari also has built-in support for [Render](https://render.com). Run the deploy command to generate the configuration files:

```terminal
rari deploy render
```

This creates a `render.yaml` in your project root and updates your `package.json`:

```yaml title="render.yaml"
services:
  - type: web
    name: rari-app
    runtime: node
    plan: free
    buildCommand: npm install --include=dev && npx rari build
    startCommand: npm start
    healthCheckPath: /_rari/health
    envVars:
      - key: NODE_ENV
        value: production
      - key: RUST_LOG
        value: info
```

The same `package.json` changes apply as with Railway: `scripts.start`, `scripts.build`, `engines.node`, and the `rari` dependency. `--include=dev` is needed because `NODE_ENV=production` is also set during the build, and the build tools are dev dependencies.

### Deploying to Render

1. Push your code to GitHub
2. Go to [render.com](https://render.com) and create a new "Web Service"
3. Connect your GitHub repository
4. Render auto-detects the `render.yaml` configuration
5. Click "Create Web Service"

Render is auto-detected via the `RENDER` environment variable, and the server binds to `0.0.0.0` with the platform-assigned `PORT`.

### System Dependencies

The Rust runtime requires `libfontconfig1` for image and font rendering. Render's native Node.js runtime includes `libvips-dev`, which provides `libfontconfig1` as a transitive dependency, so this should work out of the box. If you run into font-related errors, switch to a [Docker deployment](https://render.com/docs/docker) and install `libfontconfig1` explicitly (see the [Self-Hosting](#self-hosting) Dockerfile below).

## Fly.io

rari also has built-in support for [Fly.io](https://fly.io). Run the deploy command to generate the configuration files:

```terminal
rari deploy fly
```

This creates a `fly.toml`, a `Dockerfile`, and a `.dockerignore` (if you don't already have one) in your project root, and applies the same `package.json` changes as Railway. It also adds a `deploy:fly` script that runs `fly deploy`.

```toml title="fly.toml"
app = "rari-app"
primary_region = "iad"

[build]

[http_service]
  internal_port = 8080
  force_https = true
  auto_stop_machines = "stop"
  auto_start_machines = true
  min_machines_running = 0

  [[http_service.checks]]
    grace_period = "30s"
    interval = "15s"
    method = "GET"
    path = "/_rari/health"
    timeout = "5s"

[[vm]]
  memory = "512mb"
  cpu_kind = "shared"
  cpus = 1
```

The generated `Dockerfile` installs `libfontconfig1`, installs dependencies with the package manager matching your lockfile (npm, pnpm, yarn, or bun), runs `rari build`, and starts the server on port 8080 with `RARI_HOST=0.0.0.0`.

### Deploying to Fly.io

1. Install the [Fly CLI](https://fly.io/docs/flyctl/install/) and run `fly auth login`
2. Run `fly launch --no-deploy` to create the app (pick a unique name; this updates `app` in `fly.toml`)
3. Run `fly deploy`

Fly.io is auto-detected via the `FLY_APP_NAME`, `FLY_MACHINE_ID`, or `FLY_ALLOC_ID` environment variables, and the server binds to `0.0.0.0`. Set secrets with `fly secrets set NAME=value`.

## Self-Hosting

You can deploy rari to any platform that runs Node.js ≥ 24.21.0. The general steps:

```bash
# Install dependencies
npm install

# Build for production
npx rari build

# Start the server
PORT=8080 npx rari start
```

The key requirements:

- Node.js ≥ 24.21.0
- The `rari` package in your dependencies (it includes the platform-specific Rust binary)
- The `dist/` directory from `rari build`
- `libfontconfig1` installed on the host (required by the Rust runtime for image and font rendering)
- A `PORT` environment variable if your host expects a specific port

For containerized deployments, a minimal Dockerfile:

```dockerfile title="Dockerfile"
FROM node:24.21-slim

RUN apt-get update && apt-get install -y libfontconfig1 && rm -rf /var/lib/apt/lists/*

WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci

COPY . .
RUN npx rari build

ENV NODE_ENV=production
ENV PORT=3000
ENV RARI_HOST=0.0.0.0
EXPOSE 3000

CMD ["npm", "start"]
```

The server binds to `0.0.0.0` automatically on Railway, Render, and Fly.io, but defaults to `127.0.0.1` elsewhere. In a container or on any other host that needs external traffic, set `RARI_HOST=0.0.0.0` (as in the Dockerfile above) so the server is reachable.
